# Building the phone apps

Moved from `docs/mobile-builds.md` of the former monolith (`Ruchoir/ruchoir`) on 2026-11-11, and brought up to date with this repository.

**Expo Go stays the everyday tool**: it opens a JavaScript change at once and needs no build
(`pnpm start`, see the [README](../README.md)). What Expo Go cannot host (phone notifications, the
widgets, the document scanner) is in the real app, built from a version tag.

The builds are made by GitHub Actions (`.github/workflows/release.yml`), on GitHub's macOS runner for
the iPhone and its Linux runner for Android ([ADR 0001](adr/0001-native-apps.md)). Nothing of Expo's
hosted services is used, and the Expo CLI runs with `EXPO_NO_TELEMETRY=1`.

```
iPhone:   macOS runner: prebuild, archive (Release), Apple signs at export ─▶ App Store Connect ─▶ TestFlight
Android:  Linux runner: prebuild, release APK signed with Ruchoir's key ─▶ https://ruchoir.com/android/
```

The former monolith built development builds (Expo's development launcher, opening Metro) on
demand; this repository builds the app itself, in its Release configuration, on a version tag only.

## Starting a build

Push a tag `vX.Y.Z` equal to `version` in `app.config.ts`: the first job refuses a tag that does not
match. Builds never run for a pull request. The repository has no Actions minutes yet: the workflow
runs once billing or a self-hosted runner exists.

The native folders (`ios/`, `android/`) are generated by `expo prebuild` in the job and never
committed: anything native is said in `app.config.ts` or a config plugin.

The build number Apple and Google see is the workflow's run number (`RUCHOIR_BUILD_NUMBER`, read by
`app.config.ts`), so every run is above the last. Re-running a run whose upload succeeded is refused
by App Store Connect (same number): release a new version instead.

## iPhone

The job selects the newest Xcode 26 on the runner (Apple requires the iOS 26 SDK), then checks the
key against App Store Connect (`.github/scripts/check-app-store-key.mjs`, a minute rather than a
whole build to learn that a secret is wrong). It archives the app **unsigned**, signs it ad hoc
(which keeps its entitlements), and `xcodebuild -exportArchive` signs it for the App Store into an
`.ipa`. Signing goes through Xcode's cloud signing with the App Store Connect API key: Apple creates
and keeps the distribution certificate, so no certificate or profile is stored anywhere. The archive
is unsigned because Xcode's automatic signing would first ask for a development profile, which Apple
only makes for a team with a registered device.

The app embeds extensions written in Swift (`targets/`, added at prebuild by @bacons/apple-targets):
the notification service ([ADR 0002 of
`Ruchoir/hub`](https://github.com/Ruchoir/hub/blob/main/docs/adr/0002-phone-push-relay.md)) and the
widgets. Before the export, `.github/scripts/register-app-ids.mjs` makes sure Apple knows every
bundle id the build signs (`com.ruchoir.app`, `com.ruchoir.app.notifications`,
`com.ruchoir.app.widgets`) and the push capability. Each extension is signed ad hoc with its own
entitlements, `$(AppIdentifierPrefix)` expanded with the team id (Xcode, not signing, did not), then
the app.

The `.ipa` is uploaded by `.github/scripts/upload-to-app-store.mjs` through the App Store Connect
API's build uploads, with the same key, and the job waits until App Store Connect has taken it in (a
refused build fails the job with Apple's reasons). Xcode's own upload is not used: its content
delivery service refused, with "Cannot verify client's JWT headers", a team key that the API
accepted.

The build is marked for **internal testing only**: members of the Apple team install it from
TestFlight, with no Beta App Review. App Store Connect takes 10 to 30 minutes to process it, then
e-mails the account holder; TestFlight keeps a build 90 days.

### Secrets

Repository secrets (Settings, Secrets and variables, Actions), set by the account holder:

| Secret | What |
|---|---|
| `APPLE_TEAM_ID` | the team ID (developer.apple.com, membership details) |
| `APPLE_API_KEY_ID` | the key's ID |
| `APPLE_API_ISSUER_ID` | the issuer ID shown above the keys |
| `APPLE_API_KEY_P8` | the whole text of the `.p8` file, `BEGIN` and `END` lines included |

The key is a **team key with the Admin role** (App Store Connect, Users and Access, Integrations, App
Store Connect API): an individual key cannot reach the provisioning endpoints that cloud signing uses.
The `.p8` downloads only once, and Safari on an iPhone fails to download it: do it from a computer.
The job writes it to the runner's temporary folder and deletes it at the end, even after a failure.

**Replacing the key** (lost, leaked, or someone left): revoke it in App Store Connect, create a new
team key with the Admin role, and replace `APPLE_API_KEY_ID` and `APPLE_API_KEY_P8`. Nothing else
changes: the distribution certificate belongs to the team, not to the key.

### Installing

1. TestFlight on the iPhone (Apple's app, from the App Store), signed in with an Apple account that is
   a member of the team in App Store Connect.
2. Once App Store Connect has processed the build, it appears in TestFlight: **Install**.
3. Open Ruchoir and type your instance's domain.

## Android

Notifications need the Firebase project's `google-services.json` at build time: the whole file in
the repository's Actions secrets as `GOOGLE_SERVICES_JSON` (the hub's
[push relay](https://github.com/Ruchoir/hub/blob/main/docs/push-relay.md) says where it comes
from). Without it the APK builds, with a warning, and cannot be reached by notifications.

The job builds a release APK for every processor Android phones use (`./gradlew assembleRelease`),
signed with Ruchoir's upload key, and checks the signature with `apksigner`: never the generated
project's debug key, or an installed app would refuse the next update. When the variable
`ANDROID_CERT_SHA256` is set, the certificate must be that one. The key comes from the secrets
`ANDROID_KEYSTORE_BASE64` (the keystore, base64), `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`
and `ANDROID_KEY_PASSWORD`; the job writes it to the runner's temporary folder and deletes it at the
end. The APK is also kept 7 days as the run's artifact `ruchoir-android`.

Then, in the `production` environment, the APK becomes `ruchoir-<version>.apk` beside a
`latest.json`, its `SHA256SUMS.txt` is signed with Ruchoir's release key (`RELEASE_GPG_KEY`,
`RELEASE_GPG_PASSPHRASE`), and the whole goes to the website's server through its `deploy` account
(`ANDROID_DEPLOY_SSH_KEY`, `DEPLOY_KNOWN_HOSTS`, and the variable `DEPLOY_HOST`). There, the key is
bound to `release/android-publish-entry`, which can only start `release/android-publish` with a
version (their headers say how they are installed): it puts the files in
`/srv/ruchoir-android/vX.Y.Z/`, then `latest.json` at the top, last. Older versions stay. nginx
serves the folder as `https://ruchoir.com/android/`. No Play Store for now.

### Installing

1. Download `ruchoir-<version>.apk` from `https://ruchoir.com/android/v<version>/` (`latest.json`
   names the latest), and if you like check it against `SHA256SUMS.txt` and its signature.
2. Allow the browser or file manager to install apps, then open the APK.
3. Open Ruchoir and type your instance's domain.

An emulator neither vibrates nor has real biometrics or notifications: check those on a real phone.

## When a build fails

- **"The tag vX.Y.Z does not match version":** the tag and `version` in `app.config.ts` differ.
- **"The APPLE_* secrets are missing" or "The ANDROID_KEYSTORE_* secrets are missing":** see the
  secrets above, and [`AGENTS.md`](../AGENTS.md), "Releasing".
- **iPhone, "Check the App Store Connect key" fails:** its message names the secret that is wrong, or
  says the key is refused, revoked or not Admin.
- **iPhone, "No Accounts" or a provisioning error at export, the check being green:** cloud signing
  needs a team key with the Admin role.
- **iPhone, "bundle version must be higher":** a run was re-run after its upload; release a new
  version.
- **App Store Connect e-mails "ITMS-91053: Missing API declaration":** a library uses one of Apple's
  "required reason" APIs without declaring it. React Native gathers every library's own privacy
  manifest at `pod install`; add what the e-mail names to `ios.privacyManifests` in `app.config.ts`.
- **Android, "The APK is not signed with the expected certificate":** the keystore secrets do not
  hold the key whose SHA-256 is `ANDROID_CERT_SHA256`.
- **Android, Gradle runs out of memory:** raise `org.gradle.jvmargs` through a config plugin, not by
  editing the generated `android/` folder.
