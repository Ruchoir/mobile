## Common rules (every Ruchoir repository)

These rules are the same in every repository of the Ruchoir organization. The rest of this file adds
what is specific to this repository, and never contradicts this block.

### Golden rules

1. **No AI references anywhere.** Not in code, comments, commit messages, branch names, pull
   requests, docs or metadata. No `Co-Authored-By` naming a tool, no "generated by" note, no agent
   signature. `AGENTS.md` is the only AI-facing file allowed in a repository. Write and commit exactly
   as a human contributor would.
2. **European or neutral dependencies only.** No US or non-EU hosted service at runtime: no cloud
   provider, CDN, font service, analytics or outbound telemetry. For libraries, prefer a European or
   neutral community alternative when one is functionally equivalent. Check and record the origin and
   governance of anything new before adding it; when in doubt, ask. The accepted exceptions are listed
   in `Ruchoir/.github`, `dependency-exceptions.md`, and nowhere else: a repository never adds one on
   its own.
3. **English only** in the repository: code, identifiers, comments, docs, commits, branches, issues,
   pull requests. What the interface says to people lives in its dictionaries (see "Interface text").
4. **Document thoroughly.** Module docs, doc comments on public items, and a note wherever the
   reasoning is not obvious from the code. A structural decision gets an ADR.
5. **Keep the docs current, unprompted.** When a change alters a decision, the stack, the scope or a
   convention, update `README.md`, `AGENTS.md` and the relevant docs in the same change, so they never
   drift. Record a gotcha the first time it costs an hour, not the second.
6. **No em dashes (U+2014) anywhere**: code, comments, docs, commits. Use a colon, a comma,
   parentheses or a plain hyphen.
7. **Product boundaries.** A repository never imports another product's internal code. It reaches
   another product only through that product's public API or published events, and shares code only
   through a versioned package of `Ruchoir/core`.
8. **Every repository stands alone.** It builds, tests and starts without the source of any other
   repository checked out. Other services are replaced by test doubles built from their published
   contracts.

### Git and pull requests

- `main` is protected. Every change goes through a pull request, and the required checks must pass.
  A review is welcome but not required while the team is two developers.
- Branches: `feat/`, `fix/`, `refactor/`, `perf/`, `docs/`, `test/`, `build/`, `ci/`, `chore/`,
  then a short English name in kebab case.
- Commits and pull request titles follow Conventional Commits in English
  (`build|chore|ci|docs|feat|fix|perf|refactor|revert|style|test`, optional scope, `!` for a break).
  Pull requests are squash-merged, so the title becomes the commit. The one exception is code moved
  with its history from another repository: that pull request is merged with a merge commit, and the
  `conventions` check skips the merge commit's own subject (ADR 0009).
- No ticket identifiers, lot names or code names in branches, commits or pull requests: say what the
  change does.
- Never commit a secret. `.env` stays out of git; `.env.example` documents every variable.
- A contributor from outside the team signs the contributor licence agreement (`CLA.md` of
  `Ruchoir/.github`) on their first pull request; a check asks for it.

### Releases

- Each service (`propolis`, `hub`, `drive`, `calendar`, `chat`) is versioned with SemVer,
  independently of the major version of its API.
- A service's tag `vX.Y.Z` builds and publishes a signed image to `registry.ruchoir.com`, with
  release notes drawn from the commits. **A tag deploys nothing.** Every instance, the testers'
  included, is updated through the installer, like a customer's.
- These two rules are for the services. Any other repository (an app, the installer, a site) says in
  its `AGENTS.md` what its tag publishes.
- `Ruchoir/core` is released as one version: every crate and package carries it, and a product pins
  one version of `core` for all of them (ADR 0013).

### Decisions

- Each repository keeps its ADRs in `docs/adr/NNNN-short-title.md`, numbered from `0001` within it.
- A decision that touches more than one repository is recorded in `Ruchoir/.github` (`docs/adr/`), and
  each repository it affects links to it from its `AGENTS.md`.
- An accepted ADR is never rewritten: a later ADR supersedes it, and both say so.

### Licences

- Services, apps and the installer (`propolis`, `hub`, `drive`, `calendar`, `chat`, `desktop`,
  `mobile`, `installer`): `AGPL-3.0-only`.
- `Ruchoir/core`, which holds what another developer embeds in their own code (the Propolis SDK, the
  API clients, the design system): `MPL-2.0` (ADR 0014). `Ruchoir/.github`: `MIT OR Apache-2.0`.
- Each package declares its licence in its manifest. A repository holding code under two licences
  ships both texts. Fonts keep their own licence (IBM Plex, OpenDyslexic: OFL).
- The enterprise module is proprietary. It is never published, copied or vendored into a public
  repository, and a public repository never names, fetches or requires it.

### Dependencies

- Pin exact versions. Bump deliberately, to the latest stable release verified against the live
  registry, never from memory.
- Record the origin and governance of each dependency next to it in the manifest, as a comment.
- The reusable CI checks dependencies against `dependency-exceptions.md` (cargo-deny for Rust) and
  audits them for known vulnerabilities on every push.

### Security and privacy

- Strong encryption in transit and at rest. TLS everywhere, `wss://` only.
- The server never trusts the client: every request is authenticated and authorized server-side.
- Never log a password, token, secret or private content.
- A vulnerability is reported privately, through GitHub's private vulnerability reporting, never in
  an issue (`SECURITY.md` of `Ruchoir/.github`).
- Minimise data. Every service exports and deletes a person's data when Propolis announces a deletion,
  and a test proves it.

### Interface text

- The interface speaks French, English, Spanish, German, Italian and Polish. French is the source:
  what the product is written in, what a missing key falls back to, what the others translate.
- Each repository with an interface keeps its six dictionaries and runs the `i18n:check` provided by
  `Ruchoir/core`. Strings shared by several products (common buttons, common errors, product names)
  come from the shared package of `core`.
- One sentence, one key. French typography: a non-breaking space inside « » and before `?`, `:`, `;`
  and `!`.

## This repository

The mobile app for iOS and Android: one Expo app for every product, built on the packages of `core`
and the Propolis SDK.

**Status:** the app moved from `Ruchoir/ruchoir` (`apps/mobile`) with its history, and reaches an
instance through its products: sign-in with Propolis (`@ruchoir/native-client`), then each product's
API with its own access token (`src/products`). What no product serves yet is hidden; the list is in
the restructuring plan's progress section.

### Boundaries

- No hosted Expo service in anything built or shipped, and the Expo CLI runs with
  `EXPO_NO_TELEMETRY=1` (`dependency-exceptions.md`).
- Shows a product's screens only when the instance's manifest lists that product.
- Talks to an instance through Propolis and the products' public APIs only.

### Releasing

A tag `vX.Y.Z`, equal to `version` in `app.config.ts`, runs `.github/workflows/release.yml`:

- iPhone: the Release configuration, archived unsigned, signed ad hoc with its entitlements, signed
  for the App Store by Apple's cloud signing, uploaded to TestFlight (internal testing) through the
  App Store Connect API (`.github/scripts/`).
- Android: a release APK signed with Ruchoir's upload key (checked with `apksigner`), its
  `SHA256SUMS.txt` signed with the release GPG key, sent to the website's server through the
  `deploy` account, served at `https://ruchoir.com/android/` (`latest.json` and one folder per
  version). On the server, `release/android-publish-entry` is the key's forced command and
  `release/android-publish` places the files. No Play Store for now.

The build number is the run number. The repository has no Actions minutes yet: the workflow runs
once billing or a self-hosted runner exists. It needs these, recreated in the repository's settings
(never in a file):

- Secrets: `APPLE_TEAM_ID`, `APPLE_API_KEY_ID`, `APPLE_API_ISSUER_ID`, `APPLE_API_KEY_P8`,
  `GOOGLE_SERVICES_JSON`, `ANDROID_KEYSTORE_BASE64`, `ANDROID_KEYSTORE_PASSWORD`,
  `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD`; in an environment named `production`:
  `RELEASE_GPG_KEY`, `RELEASE_GPG_PASSPHRASE`, `ANDROID_DEPLOY_SSH_KEY`, `DEPLOY_KNOWN_HOSTS`.
- Variables: `DEPLOY_HOST` (the website's server), `ANDROID_CERT_SHA256` (the upload certificate's
  SHA-256, which the signature check compares when set).


### Rules

- **No hosted Expo service in anything built or shipped** (golden rule 2, `dependency-exceptions.md`): no EAS Build,
  Update, Submit or push. Native builds run on GitHub's runners ("Releasing" above). The only
  exception is the development signing Expo Go needs on a physical iPhone: an Expo account on the
  development machine, and `EXPO_DEV_PROJECT_ID` in the untracked `.env.local`, never a project id
  in the repository.
- **Anything native is said in `app.config.ts` or a config plugin.** `ios/` and `android/` are
  generated by `expo prebuild` in the build workflow and never committed. A native change (a library
  with native code, the config, an SDK upgrade) needs a new build of the app: see "Releasing" above.
- **Expo Go stays the everyday tool.** A native library Expo Go does not contain is reached only where
  it is present, so the rest of the app still opens in Expo Go; the feature then says it needs the
  real app.
- **No telemetry from the tooling.** Every Expo CLI invocation runs with `EXPO_NO_TELEMETRY=1` (the
  package scripts set it); a new script must too.
- **No deployment hostname in the repository.** The development server comes from
  `.env.local` (`EXPO_PUBLIC_DEFAULT_SERVER`, untracked).
- **An instance is reached through its products.** Signing in is `@ruchoir/native-client` with
  Propolis (RFC 8252: the authentication browser, PKCE, redirect `com.ruchoir.app:/oauth/callback`,
  one refresh token per issuer in the Keychain), from the domain the person types (the hub's
  manifest). Each product (`src/products/{hub,chat,drive,calendar}/api.ts`) is called on its own
  origin with an access token issued for it (`resource`), fetched before each request
  (`products/client.ts`). A screen calls through `useApi()`, the client of its instance; a call no
  installed product serves rejects with `ProductUnavailable` (`products/unavailable.ts`), and the
  screen that needs it is hidden. A product's tab and widgets show only when the manifest lists it
  (`installed`). The account and the organisation (members, roles, groups, invitations, licence) are
  Propolis's pages, opened with `openPropolisPage` (`products/auth.ts`).
- **A token only travels to its product.** An image or a download that the app fetches itself
  takes its headers from `authHeadersFor(api, url)`, which gives the token of the product the URL is
  on and nothing for any other host; never pass a product's headers to a URL that came from data.
- Every string a person reads goes through i18n, French first, the five other languages complete
  (`pnpm --filter @ruchoir/mobile i18n:check`).
- Colours come from `src/theme/tokens.ts`, a copy of `tokens.css` from `@ruchoir/design-system` kept honest by
  `test/tokens.test.ts`.
- **Shapes come from the theme too.** A person picks a style (Ruchoir, or the flat Aubergine, Nuage,
  Indigo, Marine), kept on the phone like the accent. `useTheme()` returns its palette (`c`), its
  derived colours (`s`: `primary`, `badge`, `edge`, `focus`, `bar`, the message card...) and its
  `shape` (radii, hairline, edge width, `flat`, the face's corner, message density). A file that needs a
  radius or a hairline declares `const makeStyles = styleCache((shape) => StyleSheet.create({...}))`
  and reads `useThemedStyles(makeStyles)`; an offset or soft shadow goes through `lift()` / `soft()`
  (`src/theme/lift.ts`), which draw nothing in a flat style; an ink edge is `s.edge`, a primary action
  `s.primary`. `test/themeUse.test.ts` fails on any file outside `src/theme/` that imports `radius` or
  `hairline` or writes a `shadowOffset`. The variants' values are checked against `tokens.css` (`test/support/resolve.mjs`, copied from the design system's tests) and for contrast (`test/styleContrast.test.ts`); the iPhone widgets keep their own copy
  in `targets/widgets/Shared.swift`, checked by `test/widgets.test.ts`.

- **Gate by permissions, never by role strings.** A control is shown on `rightsOf(space)` /
  `useRights().gates` (space level) and `useChannelGates(channel)` / `channelGates` (a channel's
  `myPermissions`: send, react, attach, pin, moderate, manage, members, delete), the same functions as
  the web (`@ruchoir/permissions-logic` of Ruchoir/core). The role string is only the fallback of an instance without
  the permissions, inside the places `test/noRoleGates.test.ts` lists, counted per file (a new
  `role === "admin"`, `"guest"` comparison, `includes(role)`, `switch (role)` or `canAdminister(` fails it). The
  fallbacks of an older instance live in `logic/spaceRoles.ts` (`legacyDoors`, `PHONE_LEGACY_CHANNEL`): a screen
  asks them, it never reads a role itself. A write the person's rights refuse is hidden, or the composer gives way to a note.

### Design consistency

The mockups (21 phone screens) are the reference; the web's design system fills what they do not
show. What every screen keeps:

- **Gutter 16**, rows of a list 10 vertical padding, 12 between the icon and the text; a row with no
  second line centres its single line.
- **Icon tiles**: 40 in lists, 32 in a sheet's rows, radius 10 (8 for 32); the header avatar is 36.
- **One empty state, `EmptyState`** (`ui/States.tsx`), the web's: the icon as a sticker (accent
  pastel, 2 px ink edge, -4 deg, hard offset shadow), a short title without a full stop, and one
  sentence saying what will appear there. `hero` for a whole screen, `compact` inside content (a
  day with nothing, a search with no result). Never a bare line of grey text. Never inside an
  inverted list (it would be drawn upside down): render it instead of the list.
- **Day headings** come from `useDayLabel` (`Aujourd'hui · mardi 13 octobre`, else `Mercredi 14
  octobre`), and a list of events is grouped by day with `groupByDay`, wherever it appears.
- **Dates on rows**: a conversation shows the time today (`listStamp`), a file the day as a word
  (`dayStamp`: aujourd'hui, hier, the weekday, then the date).
- **Pills and segmented controls** come from `Chips` and `Segmented`; a count in a pill is a small
  muted number, not a badge.
- **Sheet rows come from `ActionRow`** (`ui/ActionRow.tsx`): a 40 tile in a pastel, a title, a line
  under it; a destructive row in the danger colours, set apart by a hairline. Every sheet uses it.
- **A form that slides up** (people picker, new group, invitation) is a `modal` screen with
  `SheetHeader` (its title and a close button); a choice among a few things is a `formSheet` of
  `ActionRow`s.
- **A tab's own action floats** at its bottom right: `FloatingButton` (`ui/FloatingButton.tsx`),
  "New message" over Discussions, "New event" over the Agenda. Its list keeps 96 of room under it.
- **Confirmations and failures elsewhere** go through `useToast()` ("Texte copié", "Réaction non
  enregistrée"); a question that needs an answer is an `Alert`. A toast reporting a failure passes
  `"failure"` (`toast(text, "failure")`), one closing something long the person submitted `"success"`.
- **Haptics come from `feel()`** (`ui/haptics.ts`), never from `expo-haptics` directly: one feel per
  kind of moment, the table in `logic/haptics.ts` (Apple's and Android's documented meanings; Android
  uses the system's haptic constants, never the vibrator). `menu` for a long press that opens
  something, `choice` when a choice changes (`Segmented`, `Chips` and `Toggle` play theirs), `refresh`,
  `send`, and `success` / `failure` / `warning` for outcomes. Never on scrolling, tabs, opening a
  screen, copying, typing, a one-tap action whose toast is enough, live events, or the camera.
- Check a change against the mockup side by side before calling it done (`docs/specs/mobile/mockups`).

### Gotchas

- **Route names are lower camel case** (`today`, `fileViewer`): the i18n audit reads a capitalised
  single word as prose.
- **The audit only sees literal keys**: `t("a.b")` or `key("a.b")`. A key chosen at run time goes
  through a table of `key(...)` (see `session/failureText.ts`), and a ternary is written
  `cond ? t("a") : t("b")`, never `t(cond ? "a" : "b")`.
- **No `Date.now()` or `new Date()` for "now" in render** where the lint can see it: `useNow()`.
- **`useLoad` keys name what is loaded** (`"conversations:<space>"`); a new key never shows the old
  key's data, which is what keeps a space switch from painting the previous space.
- **Every write shows at once and says when it fails.** A message goes through the outbox
  (`compose/useOutbox.tsx`), which recognises its own message when it arrives live, since the API
  takes no idempotency key: never re-send an item `arrivedIds` has matched. Reactions for one
  message and emoji go out in order (`compose/useReact.ts`).
- **A sheet is its own screen** (native `formSheet`), so it cannot call into the conversation under
  it: it emits a `patched` realtime event for what it changed, or asks through `compose/requests.ts`
  (edit a message, add files) keyed by the composer's `draftKey` (`<conversation>` or
  `thread:<root>`).
- **A sheet's root is one scroll view** (`Sheet`, or a `ScrollView`/`FlatList` whose head is pinned
  with `stickyHeaderIndices={[0]}`). On iOS a `formSheet`'s content has no set height
  (react-native-screens lays it out absolutely, without a bottom), so a `flex: 1` root with a fixed
  head and a list filling the rest draws the list under the head. The keyboard has the same kind of
  trap: use `ui/KeyboardArea` (a chat, a list) or `ui/KeyboardForm` (a form), not
  `KeyboardAvoidingView`. A `KeyboardArea` must run to the bottom of its screen and rises by the
  keyboard's whole height, measuring nothing (a view's place in the window, as React Native reports
  it, leaves out the offset of the sheet it is in); give it `safeBottom` rather than wrapping it in a
  `SafeAreaView` with a bottom edge. Its height comes from react-native-keyboard-controller
  (`useKeyboardHandler`, under the `KeyboardProvider` of `App.tsx`), which reads the keyboard's real
  position at every frame, so whatever it holds moves with the keyboard; a function run there
  (`areaPlacement`) starts with the `"worklet"` directive. Not Reanimated's `useAnimatedKeyboard`: it
  guesses the keyboard's position from a curve, and the composer trailed iOS 26's keyboard. A chat's
  area is a `composer` one that `slide`s while its list shows: it moves with the keyboard and takes
  its new size only once the keyboard rests. Never resize a list at every frame: each frame
  re-renders it, Reanimated holds its own updates while React commits, and the composer falls
  behind the keyboard.
- **Every field stays in sight above the keyboard.** A form is a `KeyboardForm`, its button passed
  as its `footer`: the library's `KeyboardAwareScrollView` scrolls the focused field up along with
  the keyboard, frame by frame, and the footer rides on the keyboard. Never scroll to a field once
  the keyboard has risen (`keyboardDidShow`): the field stays behind the keyboard until then. A list
  under a search field gets `automaticallyAdjustKeyboardInsets`, so its last rows can still be
  scrolled above the keyboard. A long list of people is a `PeopleList` (a `FlatList`), never rows
  mapped inside a form.
- **Thread replies never enter a feed.** `screens/discussions/feed.ts` keeps a conversation's and a
  thread's messages live; a reply moves the count under its root once (`replyDelta`).
- **Taking the reader to a message** (a tap in the pinned tab) goes through the conversation's
  `focus`: the feed fetches older pages until it holds it (`logic/seek.ts`, pages of 100, 30 at most),
  scrolls it to the middle and lights it (`highlighted`, `ui/Flash.tsx`), then lets the focus go so
  coming back to the tab does not jump again. A reply is reached through its root, then its thread
  (`focusId`). There is no endpoint for one message or for "around a message".
- **Seeded files of the dev database have no bytes** in the dev object store: opening one answers
  404 there, on the web as well. Upload a file to test the viewer.
- **A form whose sheets change it keeps its draft outside itself.** The event form opens its draft in
  `screens/agenda/form/draftStore.ts` under a `formKey` it hands to every sheet it opens (each sheet is
  a screen of the root stack, as all sheets are); the sheets read it with `useDraft` and change it with
  `updateDraft`, and the form closes it when it goes. A choice a sheet hands back to the screen under
  it (the scope of a change to a series) goes through a small listener bus, as the composer's
  requests do (`form/scope.ts`, `compose/requests.ts`).
- **Dates and times come from the phone's own pickers** (`@react-native-community/datetimepicker`, the
  version Expo Go ships): in a sheet on iOS (`PickerSheet`, `inline` for a day, `spinner` for a time),
  as the system's dialog on Android (`DateTimePickerAndroid.open`). A picker works on the phone's
  clock: `form/when.ts` hands it a day at noon and a time on a fixed day, and reads the same local
  fields back, so no time zone shifts them. The draft keeps the event's own zone (`tz`).
- **The calendar's logic is the web's** (`src/logic/shared/calendarLogic`: time in a zone, rules and
  their phrases, reminders and their words). Its keys are looked up in this app's dictionaries too:
  `useSharedT()` hands it `t`, and the audit scans it with the app.

- **Uploads to a space live above the screens.** `uploads/UploadsProvider.tsx` holds the queue
  (`logic/uploadQueue.ts`) and sends one file at a time (`startFileUpload`, or
  `startFileVersionUpload` for a new version), so leaving a folder does not stop them; the lists
  reload through the live `files` event. A name already taken asks first (`ConflictSheet`, the web's
  replace / keep both / skip); the strip (`UploadStrip`) and the uploads sheet show the rest. Expo Go
  has no background upload: leaving the app stops what is going, which then reads as failed.
- **A scanned document is photos made into a PDF on the phone** (`ScanScreen`: `expo-image-manipulator`
  shrinks each page, `expo-print` lays them on A4 sheets through `logic/scan.ts`'s HTML). Expo Go has
  no document scanner (edges, perspective); the real one waits for the native app.
- **The office editor is a web view posting the session's form** (`OfficeEditorScreen`, see
  `docs/office-editing.md`, "Phone client"): the page's `parent` is replaced on the main frame only,
  never in its inner frames, which still need theirs.
- **A file's menu is the web's** (`EntryMenu`, the shared `actionsFor` and `canManage`): its sheets
  are routes given the `SpaceFile` itself (`fileMenu`, `fileName`, `fileMove`, `fileVersions`,
  `fileShare`, `fileSendTo`, `fileLinks`, `fileDetails`). A favourite is not broadcast: the menu emits
  a local `files` event so the lists show it.

The dictionaries check (`i18n:check`) waits for the move to `@ruchoir/i18n`.
- **Before sign-in the app is its own stack** (`navigation/AuthNavigator.tsx`, its own
  `NavigationContainer`): welcome, tutorial, sign-in. The sign-in only takes the instance's domain;
  everything else (password, second factor, passkeys, sign-up, forgotten password) is Propolis's,
  in the authentication browser. A `signedOut` with a `reason` opens on sign-in, anything else on the
  welcome.
- **A grant that ends signs the instance out.** The native client says so when a refresh token is
  refused (`signed_out`, `session_ended`); the product transport then answers 401 and the accounts
  mark the instance signed out (`expired`).
- **Preferences are read before the first screen** (`prefs/store.ts`, `loadPrefs` in `App.tsx`):
  `useTheme` takes the style, accent and mode from them, `Text` and `TextField` scale with the text size, and a
  forced day or night is also handed to the system (`Appearance.setColorScheme`) so its own controls
  follow. The notifications are the account's, on the server, as the web's. **So are the language and
  the agenda's settings** (`MOBILE_ACCOUNT_KEYS`, wire keys shared with the web where they are the
  same setting): `setPrefs` queues and sends a change to every signed-in instance, one send at a time
  (`AccountPrefsSender`); each instance's scope reads the account at sign-in and after every
  reconnection (`useResync`), merging the first time this phone syncs with that account and taking
  the server's values afterwards, and adopts `preferences.updated` by reading the document again,
  passing it on to the other instances (`AccountPrefsSync`). The look (mode, accent, text size)
  stays the phone's.
  A private conversation hidden on any device is out of the Discussions list (`hidden`); a long press
  hides one, where the instance lists `account_preferences`.
- **Every list on screen follows the live events.** `realtime/events.ts` relays every event the
  server pushes and the app draws (`handlersFor`, tested), and `affects` says which events change
  each kind of list (a space's conversations, people, channels; a channel's people; a conversation's
  pins). A new `useLoad` that shows server data gets its `useReloadOn` with that rule, or with the
  event that changes it (`calendar`, `files`). Who is online is laid over the rows as heard
  (`withLivePresence`), not reloaded. Check against the dev instance with two seeded accounts, one
  listening through the API, the other acting.
